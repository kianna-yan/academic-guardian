# 学业护航 · Academic Guardian

> 面向高校的**学业预警智能体**。以学生端为主视角，同时覆盖辅导员、教务、家长、任课教师四个协同角色，共五个端。

![状态](https://img.shields.io/badge/状态-开发中-blue)
![技术栈](https://img.shields.io/badge/FastAPI%20%2B%20Vue%203%20%2B%20Hybrid%20RAG-informational)
![许可](https://img.shields.io/badge/license-MIT-green)

**核心主张：把"期末数挂科"变成"期中看见风险，并且知道该做什么"。**

现有高校的学业预警基本是结果性统计——学期末统计不及格学分，超线就发告知函、通知家长。此时学生已经挂了一学期，干预窗口早已关闭。本项目用过程性数据（出勤、作业、期中、平台行为）提前 8–10 周识别风险，并把"为什么"和"怎么办"一并给出。

## 核心能力

- **六维加权风险评分**：课堂出勤、作业提交、期中成绩、学习投入、历史欠账、学分进度六项加权，权重与阈值全部配置化，**任意一分的来源可手工复算**
- **可解释归因**：不只给总分，还给每项贡献分与扣分理由——学生能看清是哪门课、哪个环节把自己推进风险区
- **成因分型，不是模板填空**：先按跨指标行为组合判定成因（基础薄弱 / 投入不足 / 状态异常 / 单科短板 / 历史欠账 / 回升观察），再让每条建议引用这名学生自己的证据——哪天哪节课缺的、哪次作业几号截止、任课老师什么时候答疑
- **数值不经模型**：挂科、学分缺口等确定性条件走硬规则，六项分数由本地函数计算；**模型不可用时风险评分、归因与行动清单仍完整可用**
- **一校一规混合检索**：BM25 稀疏通道 + 向量稠密通道各自召回，用 RRF 融合后重排，返回结果**必须带条款出处**（文件 · 章节 · 相关度 · 命中原因），拒绝无源引用；教师上传的真题与讲义自动解析进同一套索引
- **每条回答都能点开看出处**：回答正文标 `[1] [2]` 编号，下方「引用资料 N 条」可展开逐条核对，顶部轨迹条显示改写后的查询、两路通道候选数与检索耗时
- **多模态也能记住**：发一张成绩单截图或成绩表照片，视觉模型识别后写入会话材料记忆；接着追问细节时会**把原图重送视觉模型复核**，不会「问完就忘」；也支持按住说话转文字
- **五端独立鉴权**：学生 / 辅导员 / 教务 / 家长 / 教师各自登录，权限在服务端拦截——学生访问别人学号得 `403`，辅导员改不了规则，教师只看得到自己课堂
- **每个数字都能往下追**：考勤落到每一节课的日期与节次、作业落到每一次的截止日与提交状态、课程落到任课老师的邮箱与答疑时间
- **文书与数据导出**：Word 告知函 / 家长信 / 谈话要点 / 干预记录、PPT 学期报告、CSV 名单；未配 SMTP 时自动产出 `.eml`
- **消息中心与异议闭环**：旷课、作业未交、预警提醒推送到学生端；学生可对待办提异议，流转到辅导员端就地裁定，回执回到学生端并自动闭环
- **课表 → 课后 10 秒自评 → 学习轨迹**：课表由排课数据现算，已上过的课点开就能记「听懂 / 有点模糊 / 没听懂 + 从第几分钟开始 + 卡在哪个知识点」；记录连成每门课一条轨迹线，连续两节以上没跟上标成断点，后面接上了留一圈修复环
- **每个学生一棵智慧树**：一颗果实一门课，果实颜色区分学科（可切换成按分数段着色），大小是学分，点开看单科面板；树根对应六个评分因素，树冠浓密程度跟着整体状态走
- **成绩分配试算台**：按学科性质给五套考核权重（理论必修 / 语言 / 思政人文 / 项目制选修 / 实验实践），每一项的起点分都来自学生自己的真实数据；学生自己拖分、自己改占比，总评与"会不会挂"实时重算，还会算出"期末至少要考多少分"
- **模块分区导航**：学生端按「学习空间（每节课都在用）/ 我的成长（看得见）/ 学业档案（看结果）/ AI 顾问（随时问）」分区，其他端各自成区，功能不再平铺成一长条

## 技术栈

| 层 | 选型 |
| --- | --- |
| 前端 | Vue 3.5 + TypeScript 5.6 + Vite 6，vue-router 4 登录守卫，Pinia 2 状态管理 |
| 组件与图表 | Element Plus 2.9（表格 / 抽屉 / 弹窗 / 表单）、ECharts 5.5（按需引入 Pie + Bar） |
| 通信 | axios（拦截器统一附加 token）+ 原生 `fetch` 读流（SSE over POST） |
| 鉴权 | 自建轻量账号体系：PBKDF2-SHA256 密码哈希 + HMAC 签名 token + 中间件按角色拦截 |
| 服务 | Python 3 + FastAPI，64 个接口 + SSE 流式响应，单容器托管前端产物 |
| 传输 | GZip 压缩静态资源（全部 chunk 2450 KB → 761 KB）；SSE 走 chunked 不压缩，保证逐 token 推送 |
| 构建 | Vite 6 代码分割（路由懒加载 + 按 node_modules 分组），Element Plus 按需引入 |
| 检索 | 自实现混合检索：BM25（k1=1.5 / b=0.75，jieba + 学业词表）∥ 向量（`embedding-3`）→ RRF 融合 → 重排；向量通道不可用时自动降级为本地字符 n-gram |
| 导出 | python-docx 生成 Word、python-pptx 生成 PPT、标准库生成 CSV 与 `.eml` |
| 模型 | 可选接入任意 OpenAI 兼容接口；作答与路由分模型；**LLM 仅负责组织语言，不参与任何数值计算** |
| 多模态 | 视觉模型识别成绩单/截图并写入会话记忆，细节追问时原图复核；语音按住说话走 ASR |
| 数据 | 240 名学生模拟数据（固定随机种子），无数据库；账号库与课程档案落 JSON 文件 |

**首屏做了什么：** `index.html` 预置骨架（Vue 挂载时自动清空，无需卸载逻辑）；静态资源走 gzip；Element Plus 按需引入；路由级懒加载让图表库不进首屏。实测首屏 gzip 后约 474 KB，其中 Element Plus 占 250 KB——表格、抽屉、弹窗、选择器都是真用到的组件，再压就得砍功能了。

## 一、要解决的问题

| | 现有做法 | 本项目 |
| --- | --- | --- |
| 时点 | 学期末，出成绩之后 | 第 8 教学周，期中之后 |
| 依据 | 不及格学分是否超线 | 六维过程性数据加权 + 硬规则 |
| 输出 | 一张告知函 | 风险等级 + 归因拆解 + 编号行动清单 |
| 干预窗口 | 已关闭 | 还有 8–10 周 |

**这不是"预警得不准"的问题，而是"预警得太晚、且只告诉结果不告诉原因"的问题。** 而这个问题的解法必须同时具备三件事：多维度数值计算（规则引擎擅长）、非结构化校规检索（关键词搜索做不好）、个性化语言生成（模板写不出来）——只有把三者串起来的 AI 系统能做成。

## 二、五个端各做什么

| 角色 | 核心价值 | 主要功能 |
| --- | --- | --- |
| **学生端（主）** | 自查 + 补救 | 风险分与等级、六因素归因、课程级挂科概率、编号行动清单、逐日考勤、作业清单（欠什么、几号截止）、任课老师联系方式、课表与课后自评、学习轨迹、智慧树、成绩分配试算、历年真题与网课、可追问的对话助手、复核申请 |
| **辅导员端** | 减负 + 闭环 | 按风险排序的名单（每人一句"本周先做"，按成因分型而非套模板）、班级/等级筛选、学生画像抽屉（归因判断 + 判断依据 + 可转介资源 + 复查节点）、一键生成谈话要点、干预记录留痕、班级周报 |
| **教务端** | 规则 + 全局 | 风险分布看板、班级对比、预警阈值在线配置并实时重算、课程与教师档案导入、批量开通学生账号、预警名单导出 CSV |
| **家长端** | 沟通 + 合力 | 学生状态通俗解读、学校已做的帮扶、家长配合建议、家长信生成 |
| **教师端** | 教学侧观察 + 资源供给 | 自己课堂的学生画像与风险分布、按课程看班级学情、上传历年真题与网课资料（自动解析进 AI 知识库，学生问得到） |

五端共用同一套评分引擎与知识库，只是视图和话术不同。

### 2.1 登录与账号（五端相互隔离）

五个端不再共用一个页面，各自独立登录，登录后只能进自己的端。

| 端 | 账号 | 初始密码 | 说明 |
| --- | --- | --- | --- |
| 学生端 | 学号（8 位，如 `20240067`） | `0000` | 只能看本人数据 |
| 辅导员端 | `2024014589` | `1111` | 看全校名单但改不了规则 |
| 教务端 | `1234567899` | `2222` | 规则配置 + 账号开通 + 导出 |
| 家长端 | 孩子学号 | `3333` | 只能看这个孩子 |
| 教师端 | `2024014501` | `4444` | 只看自己任教的课程与学生 |

- 登录页把五个账号的初始密码直接印在下方卡片，点一下自动填入，评审不用问就能试。
- 每个端登录后顶栏右上角都有**修改密码**；仍在用初始密码时，内容区顶部常驻一条提醒。
- 教务端支持**批量开通学生账号**：粘贴 `学号,姓名,班级` 或上传 CSV/TXT，已存在的学号重置回初始密码，学号不在学情库里的行逐条报错。
- **权限在服务端挡，不只靠前端路由**：学生/家长访问别人学号 → `403`；访问全校名单、班级报告、全校看板、规则配置 → `403`；辅导员改规则、开账号 → `403`；教师访问别人的课堂、上传以外的接口 → `403`；未带 token 访问任何业务接口 → `401`。
- 实现：`engine/accounts.py` 用 **PBKDF2-SHA256**（12 万轮）存密码哈希，登录态是 **HMAC 签名 token**（12 小时有效），账号库落在 `data/accounts.json`，改密与导入能跨重启保留。

### 2.2 考勤、作业与课程明细

学生端不只有"缺勤 17 次"这种汇总数字，每个数字都能往下追到明细。

- **逐日考勤**：每门课已上的 14 节课都落在具体日期上（第 1–7 周、每周两次），带星期、节次、状态（旷课 / 迟到 / 出勤）与说明。默认只显示异常，可一键切"全部 84 次"。**汇总由明细派生**，所以记录条数和预警用的缺勤次数永远一致，不会出现"表格说缺 17 次、明细只列 12 条"。
- **作业清单**：每门课 6 次作业，列出标题、要求、布置日、截止日、状态（已交 / 迟交 / 未交）与提交时间，未交的按逾期天数排最前。
- **任课老师**：每门课一张卡，显示姓名、职称、学院、办公室、邮箱、电话与答疑时间，邮箱电话是可点的 `mailto:` / `tel:` 链接。
- **教务端维护课程与教师**：粘贴或上传一份清单即可，课程代码已存在则更新联系方式（留空字段保留原值），新代码作为"待开课"课程出现且不参与预警计算；每行独立校验代码格式、学分范围、邮箱格式，错误逐行返回行号与原因。落盘 `data/curriculum.json`，导入后立刻生效，无需重启。

### 2.3 课表、课后记录与学习轨迹

风险分告诉你"现在有多危险"，但学生真正想知道的是"我从哪一节课开始听不懂的"。这一块单独成区，数据也单独存放。

- **我的课表**：由 `engine/data.py` 的排课 `slots` 现算，和「学情总览 → 课堂考勤」里的每一条记录同源，不会出现"课表说周三有课、考勤里没有"。周次可前后翻，今天那列高亮；每格标出这节"记过没有 / 听懂了 / 模糊 / 没懂"。
- **课后 10 秒记录**：点已上过的课 → 三个问题（听懂没有 / 从什么时候开始没听懂 / 之后打算怎么办），全部点选，最慢 10 秒填完。填的过程中下方实时拼出"系统会记成什么"，学生知道自己写了什么。记录落 `data/checkins.json`，可改可删。
- **学习轨迹**：每门课一条横线，一节一个点，颜色就是那天课后的判断；**连续两节以上没听懂才算断点**（一节课跟不上很正常），断点后面第一次听懂，那个点留一圈修复环。断点、修复、建议、记录流都在同一页。
- **设计红线：打卡不进风险分**。学生诚实说"没听懂"，只会得到更清楚的轨迹和更具体的求助路径，不会因为自评差被扣分；页面上把这句话写死，位置就在统计数字旁边。
- **口头也能问**：智能体多了一个 `get_learning_track` 工具，问"我从哪节课开始没听懂""哪门课最该补"，回答里的周次、节次、知识点都来自上面的记录，不是模型编的。

### 2.4 智慧树与成绩分配试算

前一块讲"这节课听懂没有"，这一块讲"整个学期长成什么样"。

- **我的智慧树**：手绘风 SVG，一颗果实一门课。果实颜色默认是学科专属色（同一门课在所有人的树上都是同一个颜色，便于对照），顶上一键切「按状态」就变成红黄绿；外圈光晕始终表示分数段，果实大小表示学分。点果实，右侧面板给出期中卷面、班级均分、挂科概率、本期变化和本学期五次测评。
- **两套口径摆在一起**：果实颜色看的是最近一次测评分数，面板里的挂科概率来自风险引擎（按出勤、作业综合算），两者会打架——一个学生期中 82 分但旷课 17 次，概率是 99%。页面不藏这个矛盾，直接写明"分数是果子的颜色，出勤和作业是它的根"。
- **成绩分配试算台**：五套考核权重按课程性质分配（理论必修重期末、项目制选修重项目产出、思政课重平时参与），每一项的起点分全部从学生自己的明细推出来——随堂测取 4 次均值、平时按出勤与迟到折算、作业按提交率折算，期末还没考就按"期中 + 本期趋势"估一个参考值并标注为估算。
- **判定两条线**：加权总评 ≥ 60 且期末卷面 ≥ 45（常见校规，页面写明是演示口径）。不通过时直接算"期末至少考多少分"，`> 100` 就显示"期末满分也救不回来"。权重可以自己改，改完按比例归一、总评立刻重算。
- **红线：试算不进风险分**。存下来的只是"分配方案"（分数与权重，落 `data/simulations.json`），结论全部在前端算，不给辅导员看，也不会影响预警。

### 2.5 教师上传的资料，学生问得到

这是"资源"与"知识库"之间的那段路——很多同类系统只做到"能下载"，AI 却读不到。

- **教师端上传**：在「历年真题 · 网课」里选类型（真题 / 讲义）、填课程与说明，上传即存盘，元数据落 `data/teacher_resources/index.json`。
- **自动解析入库**：上传成功后立刻抽正文（`txt` / `md` / `docx` / `pdf`），按原文标题切成章节，重写成一篇带 front-matter 的知识库文档，落到 `knowledge/resources/res-<id>.md`，然后**后台重建索引**。教师端列表每份资源带绿色小标「已入 AI 知识库 · N 段」，不能解析的（视频、压缩包、扫描件）显示黄色「未入库 · 原因」，文件仍可正常下载。
- **删资源即删索引**：删除文件会同步清理知识库文档并重建，不留"点得开但已删"的引用。
- **学生问得到**：问「去年数据结构期末考了什么」「讲义里 Dijkstra 复杂度是多少」，回答会引用老师上传的原文，并提示到「学习资源」下载原件。资料里只有题目没有答案时，明确说"只有题目、没写答案"，不编答案。
- **不抢结构化问法**：「明天有没有数据结构课」仍走课表，不会被资料检索挤掉——所以只有 `material` 意图或规则引擎认不出时才去翻资料库。

## 三、为什么必须是 AI 原生

| 环节 | 传统做法 | 本项目的做法 | 去掉 AI 会怎样 |
| --- | --- | --- | --- |
| 风险归因 | 超线即预警，只报数字 | 六因素加权拆解，每项贡献可复算 | 学生知道"62 分"，不知道"该补出勤还是补作业" |
| 校规匹配 | 关键词全文搜索 | BM25 + 向量双通道召回，RRF 融合并重排，回答下方附条款出处与相关度 | "我 15 学分挂科算不算降级"这类问题搜不到 |
| 材料理解 | 只存文件名 | 上传即解析入知识库；截图/照片走视觉模型并写入会话记忆 | 老师发的真题学生问不出来，发过的成绩单转头就忘 |
| 行动建议 | 固定模板填空 | 按个人六因素短板生成编号清单 | 输出千篇一律，学生不会执行 |
| 文书生成 | 辅导员手写 | 谈话要点 / 家长信 / 周报按学生实际数据生成 | 一个人一天写不完 240 份 |

**关键的工程立场：所有数字由工具函数计算并返回，大模型只负责组织语言。**

成绩和预警是敏感数据，模型编一个分数就是事故。因此 Agent 层采用"意图识别 → 工具调用 → 事实拼装 → 语言润色"四段式，模型永远拿不到计算权。没有配置 API Key 时，系统用模板拼装同样能完整运行——**这不是降级方案，而是把"可信"放在"智能"之前的设计选择**。

### 流式对话与 Agent 轨迹

`POST /api/chat/stream` 返回 SSE，事件协议：

| 事件 | 载荷 | 前端如何用 |
| --- | --- | --- |
| `meta` | `{intent}` | 显示意图识别结果 |
| `thought` | `{text}` | 一句话说明"这一问判成了什么、准备去查什么"，轨迹条的第一行 |
| `tool` | `{tool,args,ms}` | 逐个点亮工具调用徽标，这就是"Agent 在思考"的可视化 |
| `delta` | `{text}` | 追加到气泡，形成打字机效果 |
| `citations` | 引用数组（出处 / 相关度 / 命中原因 / 学校） | 渲染"引用资料 N 条"，可展开逐条核对 |
| `action` | `{...}` | 回答末尾挂一张"要不要我替你做"的卡片，点了才执行 |
| `suggestions` | 字符串数组 | 刷新追问建议 |
| `done` | `{elapsed_ms,agent_ms,intent}` | 定格总耗时 |

服务端把 Agent 放在独立线程里跑，通过 `queue.Queue` 把中间事件转给生成器，所以工具调用是**真实时**推送的，不是先算完再切片。

> 已知坑：往 `ref([])` 里 `push` 的普通对象，直接改字段不触发重渲染，必须取回数组里的响应式代理再改；流式请求必须在面板收起 / 切换角色 / 组件卸载时 `abort()`，否则请求悬空还会往已卸载的视图里写数据。

## 五、风险模型

```
风险分 = Σ (权重ᵢ × 因素ᵢ归一化值) × 100     再叠加硬性规则
```

| 因素 | 权重 | 数据来源 |
| --- | --- | --- |
| 课堂出勤 | 26% | 考勤记录 |
| 作业提交 | 20% | 作业平台 |
| 期中成绩 | 20% | 教务成绩（含班级 z-score） |
| 学习投入 | 12% | 平台登录、视频完成率、最近活跃 |
| 历史欠账 | 12% | 上学期 GPA、累计不及格学分 |
| 学分进度 | 10% | 已修学分 vs 培养方案 |

**权重依据：** 上表为**初始设定**，按「过程性观测优先、结果性指标为辅」的原则分配——出勤、作业、期中三项直接反映当期学习状态，合计 66%；历史欠账与学分进度反映累积风险，合计 22%；学习投入作为补充信号占 12%。权重集中配置于 `engine/risk.py`，**各校可按自身预警口径整体覆盖**；后续以实际预警命中率与误报率做校准，不做成一成不变的固定值。

硬性规则（不允许被加权平均稀释）：

- 期中不及格 ≥ 2 门 → 直接进入红色
- 缺勤率 ≥ 25% → 至少黄色 + 15 分
- 累计不及格学分 ≥ 25 → 至少 80 分

**可解释性：** 每个因素的 `权重 × 归一化值 × 100` 就是它贡献的分数，六项相加等于风险分。学生看到的"出勤 20.2 分、作业 17.5 分"不是形容词，是可复算的加数。

**建议从哪里来：** `engine/advice.py` 先用跨指标行为组合判断成因（基础薄弱 / 投入不足 / 状态异常 / 单科短板 / 历史欠账 / 回升观察 / 多项轻度），再让每条建议引用这名学生自己的证据。同一成因下准备多组等价策略，按学号稳定轮换——所以两个人看到的话不一样，同一个人每次看到的又一致。

## 六、RAG 与"一校一规"

### 6.1 语料

`knowledge/` 下 **16 篇文档、88 个章节**，分三类：

| 类别 | 篇数 | 内容 |
| --- | --- | --- |
| 校级规定 | 5 | 华南理工、北京科技大学、上海理工、深圳技术大学、上海海事——各自的预警学分线、降级条件、重修与退学处理 |
| 教育部政策 | 1 | 通用学籍与学业预警要求 |
| 通用规定与办事指南 | 10 | 学籍管理整理稿、系统评分口径，以及缓考补考、重修、考勤请假、推免升学、奖助学金、申诉与家庭困难、心理帮扶、办理指引、常见问题 |

每篇带 front-matter（学校 / 文件 / 生效日期），正文按 `##` 分节，一节就是检索的最小单元，引用时能精确到「《学籍管理规定》· 降级试读的条件」这一级。

**换一所学校只需新增一个 md 文件**——"一校一规"是本项目相对通用产品的差异点：华南理工是 15 学分预警、25 学分降级，北京科技大学是单学期不足 14 学分警示，深圳技术大学是学分不足所选二分之一，规则完全不同。**通用的"学业预警"产品在这里会直接失效，因为判定标准由每所学校自己定。**

### 6.2 检索：两条通道 + 融合 + 重排

```
查询 ──► 同义词扩展（挂科→不及格/补考/重修；保研→推免）＋ 上一轮用户原话补全省略句
         ├─ BM25（jieba + 60 词学业词表，k1=1.5 / b=0.75）
         └─ 稠密向量（embedding-3，2048 维）
              └─ RRF 融合（k=60）
                   └─ 重排：标题命中 ↑、idf 加权正文覆盖 ↑、学校匹配 ↑、短块惩罚 ↓
                        └─ Top-K + 归一化相关度
```

三个细节决定了效果：

- **分词必须带领域词表**。字符 bigram 会把「还能」「金吗」这类碎片算成命中，正文覆盖率被灌水。同一知识库、同一评测集，bigram 基线 Recall@1 只有 81.1%，换成 jieba + 学业词表后 94.6%——这是本项里影响最大的单点。
- **命中要按 idf 加权**。否则「什么情况可以申请缓考」会被「什么情况必须补考」抢走——专有词一票应当顶白话词多票。
- **查询要改写**。「那保研呢」这种省略句，靠同义词表 + 上一轮原话补全，才不会检索成空。

### 6.3 回答里怎么用

回答正文里每条结论带 `[1] [2]` 编号，下方一行「**引用资料 N 条**」，点开逐条显示：出处（《文件》· 章节）、**相关度百分比**、**命中原因**（标题命中几个词 / 正文覆盖率 / 学校匹配）。顶部轨迹条另有 `retrieval` 元信息：改写后的查询、两路通道候选数、走的哪条通道、耗时。

**没有检索就没有可点开的出处**——这是评委最容易验证的一点。

### 6.4 教师上传的资料也进这套索引

见 §2.5。上传即解析入库并重建索引，删除即清理；问答时 `kind="resource"` 与政策条款分开走，互不挤占。

### 6.5 评测：37 条标注问法

`tests/rag_eval.py` 是人工标注的 37 条问法（口语化、带省略、跨校混淆），跑三种配置做 ablation：

| 配置 | Recall@1 | Recall@3 | MRR@3 | 平均耗时 |
| --- | --- | --- | --- | --- |
| A 纯 BM25（基线） | 94.6% | 100% | 0.964 | <1 ms |
| B BM25 + 查询改写 | 86.5% | 100% | 0.928 | <1 ms |
| C 混合检索（线上） | **97.3%** | **100%** | **0.986** | 419 ms（首次）/ 8 ms（缓存） |

两点值得说：一，Top-1 从 94.6% 提到 97.3%，MRR 0.986 说明命中的第一名基本就是该给的；二，B 反而比 A 低——改写扩词会把长句的噪声一起带进来，所以线上只在**上一轮上下文存在**时才改写，不是无条件扩。

`python -m tests.rag_eval --detail` 可看每条未命中的具体原因。完整设计说明见 [`docs/RAG.md`](docs/RAG.md)。

接入后侧边栏徽标显示"大模型已接入 · 模型名"。未接入时显示"规则引擎模式"，功能不缺失——检索会退回本地字符 n-gram 向量，意图路由退回规则链。

**如何确认确实连上了**（三处可查，都不需要看代码）：

1. 侧边栏底部徽标：`大模型已接入 · glm-5.3-flash`；
2. 开启浏览器开发者工具的 SSE 事件流，`POST /api/chat` 会返回 `thought` / `tool` / `delta` 事件，`meta.intent` 为 `llm_route` / `llm_tool` 说明这一问是模型自己决定取数的；
3. 直接请求 `GET /api/llm/status`（需登录 token），返回 `{"enabled":true,"ok":true,"model":"glm-5.3-flash","route_model":"glm-4.5-air"}`。

同一批问题在两种模式下的差别：接入前所有拿不准的问法都会落到同一句能力清单；接入后模型自己发起工具调用，回答里带具体数字与归因。

**模型在流程里的位置**。这套系统不是"模型自由发挥"，模型被放在**决策位**：

```
用户问题 → 规则引擎能不能确定地答？
             ├ 能（问风险分、问名单、问校规）→ 规则取数 → 模型只组织语言
             └ 不能（问方法、问边界、问法模糊）→ 模型自己判断
                                                  ├ 需要数据 → 发起工具调用 → 结果回填 → 作答
                                                  ├ 不需要   → 直接作答
                                                  └ 判断不了 → 回落规则引擎，行为与改造前一致
```

`engine/tools.py` 是模型能调用的全部工具（21 个），每个都带角色权限：

| 工具 | 作用 | 学生/家长 | 辅导员/教务 | 教师 |
|---|---|---|---|---|
| `get_student` `get_risk` `get_attendance` `get_homework` `get_courses` `get_timetable` `get_scores` `get_final_forecast` `get_todos` `get_letter` `get_interventions` `get_appeals` `get_curriculum` `get_learning_track` | 单人学业数据与流程（14 个） | **只允许本人** | ✅ | 仅本人任教课程内的学生 |
| `get_class_scores` | 单科班级分数分布 | 降级为**只看自己名次** | ✅ | 仅本人任教课程 |
| `get_class_report` | 班级学情简报 | ✗ | ✅ | 仅本人任教班级 |
| `get_roster` | 风险名单 | ✗ | ✅ | ✗（改用 `get_classroom`） |
| `get_classroom` | 自己课堂的画像 | ✗ | ✗ | ✅ |
| `get_overview` | 全校统计 | ✗ | ✅ | 只给总量，不给逐班 |
| `get_messages` | 家校 / 师生消息 | 家长 ✅、学生 ✗ | ✅ | ✗ |
| `search_policy` | 校规与教师资料检索（混合检索） | ✅ | ✅ | ✅ |

**为什么要有 `LLM_ROUTE_MODEL`。** 实测 GLM-5.3-Flash 出第一个 token 要 4～11 秒
（它是推理模型，每次调用都先思考），GLM-4.5-Air 只要 0.7 秒。而"该调哪个工具"
"把工具结果说成话"这两件事不需要深推理。分开之后同一批问题的平均耗时从 8.0 秒降到 5.2 秒。
留空则全部用 `LLM_MODEL`，行为正确但会慢。

**评测**。`python tests/chat_eval.py` 跑 38 条用例，覆盖取数题 10 条、课表题 10 条、通用题 6 条、边界题 6 条、成绩题 6 条，逐条判定"该调工具时调了没有、数字对不对、该拒答时拒了没有"。改造前这些问法全部落在同一个 `unknown` 分支、输出同一段硬编码话术（不同回答数 = 1）；现在 38 条互不相同。

最近一次实测 **37/38**，平均 3.7 秒；唯一未过是「明天天气怎么样」这类边界问法，措辞波动导致关键词没踩中，实际回答仍是"我无法查询天气信息"。检索侧另有 `tests/rag_eval.py` 37 条标注问法，见 §6.5。

## 十、数据说明与合规

当前使用**确定性生成的模拟数据**（固定随机种子，每次启动一致）：240 名学生、6 个班、6 门课、第 8 教学周，含上学期 GPA 与挂科记录。

这样做的原因：真实学情数据受《个人信息保护法》与校级数据管理规定限制，比赛阶段无法获取，也不应获取。数据层是独立的 `data.py`，接口形态按真实教务系统字段设计，替换为真实数据源时上层的评分、RAG、文书逻辑不需要改动。

**风险分布：** 红色 8 人（3.3%）、黄色 37 人（15.4%）、正常 195 人（81.2%），平均分 24.0，呈「正常为主、风险长尾」的梯度形态，符合预警系统应有的分布。阈值可在教务端在线调整，改完立刻整体重算。

## 十一、边界与后续

明确不做的事：

- **系统不作出任何处分决定。** 预警只是提醒，所有升级、降级、退学均需人工核实与学校程序。
- **不做行为监控的无限扩张。** 当前只用教学相关数据（考勤、作业、成绩、平台学习行为），未引入消费、门禁、社交等数据。
- **保留申诉入口。** 学生端已实现复核申请（写入跟踪记录，状态为"待人工复核"），家长端明确提示可申诉。
- **初始密码是演示设定。** 直接印在登录页方便评审试，生产环境必须改强密码并强制首登修改；未做登录失败次数限制、找回密码、统一身份认证对接——这些依赖学校现有 IAM，不在原型范围。
- **账号库是单个 JSON 文件。** 适合单实例演示；多实例部署应换成数据库。
- **多模态只做理解，不写入成绩。** 学生发来的成绩单截图能被识别并被追问，但识别结果不会并入风险评分——评分只认教务侧的结构化数据，避免一张 P 图改变预警结论。

后续可做：接入真实教务系统 API、把访谈记录纳入模型形成"干预有效性"反馈闭环、多模态识别结果经人工确认后结构化入库（当前只做展示与问答，不落评分）。
