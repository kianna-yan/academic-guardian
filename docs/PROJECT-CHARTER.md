## 二、项目背景与问题分析

### 2.1 现状

当前高校学业预警普遍采用**结果性统计**：学期末统计不及格学分，超过阈值后发出告知函、通知家长、进入学业警示流程。

这种做法存在两个结构性缺陷：

**其一，时点太晚。** 预警在学期结束后才触发，此时学生已经挂了一学期，可干预的窗口早已关闭。即便预警生效，能做的也只是事后补救，而非事前避免。

**其二，只给结果，不给原因和路径。** 告知函告诉学生"你已进入学业警示"，却不说明是哪几项指标出了问题、各项各占多少权重、接下来该优先补哪一个。学生拿到结论，仍然不知道该做什么。

### 2.2 问题的本质

这不是"预警算得不准"的问题，而是**预警得太晚、且信息密度太低**的问题。

要解决它，必须同时具备三种能力，而这三者恰好分属不同技术范式：

- **多维度数值计算** —— 六个维度加权、硬规则约束、贡献分拆解。规则引擎擅长，大模型不可靠
- **非结构化文本检索** —— 各校学籍管理规定表述各异，学生的问题千奇百怪。关键词搜索召回差，需要语义相关性排序
- **个性化内容生成** —— 把同一份数据，讲成学生能看懂、辅导员能直接用、家长能接受的话。模板写不出来，只有生成模型能做

**单个技术都解决不了，必须把三者编排成一个系统。** 这就是本项目立项的技术起点。

### 2.3 政策与行业背景

教育部《普通高等学校学生管理规定》要求高校建立学业预警机制，但对预警的**时点、指标体系、干预方式**未作统一规定，各校自行制定细则。这带来两个结果：一是各校预警规则差异极大（有的按不及格学分，有的按单学期修读学分，有的按比例），二是通用预警产品难以落地。

这一现状既是难点，也正是本项目的切入点——**"一校一规"不是妥协，而是这个领域真实的业务形态。**

## 三、项目目标

### 3.1 总目标

构建一套**可解释、可复算、可换校**的学业预警系统：在第 8 教学周（期中之后）识别出高风险学生，并把"为什么有风险"和"接下来该做什么"一并交付给四类使用者。

### 3.2 具体目标

| 序号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 预警时点从学期末前移至第 8 教学周 | 提前 8–10 周，干预窗口仍在 |
| G2 | 风险评分完全可解释 | 六项因素贡献分相加等于总分，任一分数可手工验算 |
| G3 | 校规判定可溯源 | 每次规则类回答附学校名与条款标题 |
| G4 | 四类角色共用一套引擎 | 学生 / 辅导员 / 教务 / 家长，仅视图与话术不同 |
| G5 | 无外部依赖也能完整演示 | 未配置大模型 Key 时，规则引擎模式功能完整可用 |

### 3.3 量化指标与验收方式

| 指标 | 目标值 | 验收方式 |
| --- | --- | --- |
| 覆盖角色数 | 4 | 四端逐端走查 |
| 风险维度 | 6 | 单元测试校验六项贡献分之和等于总分 |
| 校规语料 | ≥ 5 所高校、≥ 20 条款 | 语料清单核对 + 条款检索命中测试 |
| 全量评分耗时（240 名学生） | < 500 ms | 压测脚本连续 10 轮取中位数 |
| 规则问答 Top-3 命中率 | ≥ 80% | 20 条标准问题抽样人工判定 |
| 未配置 Key 时可用功能占比 | 100% | 清空 Key 后全链路回归 |

## 四、建设内容

### 4.1 四端功能设计

| 角色 | 核心价值 | 主要功能 |
| --- | --- | --- |
| **学生端（主）** | 自查 + 补救 | 风险分与等级、六因素归因、课程级挂科概率、编号行动清单、逐日考勤、作业清单、任课老师联系方式、可追问的对话助手、复核申请 |
| **辅导员端** | 减负 + 闭环 | 按风险排序的名单（按成因分型给"本周先做"）、筛选、学生画像、一键生成谈话要点、干预记录留痕、班级周报 |
| **教务端** | 规则 + 全局 | 风险分布看板、班级对比、阈值在线配置并实时重算、课程与教师档案导入、批量开通学生账号、预警名单导出 CSV |
| **家长端** | 沟通 + 合力 | 学生状态通俗解读、学校已做的帮扶、家长配合建议、家长信生成 |

四端共用同一套评分引擎与知识库。**同一个学生的同一份数据，在四个端被翻译成四种语言**——这是产品设计的核心，也是"话术降维"这一能力的集中体现。

四个端各自独立登录、权限在服务端拦截：学生 / 家长访问他人学号返回 `403`，辅导员改规则返回 `403`，未登录访问业务接口返回 `401`。实现为 PBKDF2-SHA256 密码哈希 + HMAC 签名 token，账号库落 `data/accounts.json`。

### 4.2 风险模型

```
风险分 = Σ (权重ᵢ × 因素ᵢ归一化值) × 100     再叠加硬性规则
```

| 因素 | 权重 | 数据来源 |
| --- | --- | --- |
| 课堂出勤 | 26% | 考勤记录 |
| 作业提交 | 20% | 作业平台 |
| 期中成绩 | 20% | 教务成绩（含班级 z-score） |
| 学习投入 | 12% | 平台登录、视频完成率、最近活跃 |
| 历史欠账 | 12% | 上学期 GPA、累计不及格学分 |
| 学分进度 | 10% | 已修学分 vs 培养方案 |

**权重依据：** 上表为**初始设定**，按「过程性观测优先、结果性指标为辅」的原则分配——出勤、作业、期中三项直接反映当期学习状态，合计 66%；历史欠账与学分进度反映累积风险，合计 22%；学习投入作为补充信号占 12%。权重集中配置于 `engine/risk.py`，**各校可按自身预警口径整体覆盖**；后续以实际预警命中率与误报率做校准，不做成一成不变的固定值。

**硬性规则**（不允许被加权平均稀释）：

- 期中不及格 ≥ 2 门 → 直接进入红色
- 缺勤率 ≥ 25% → 至少黄色 + 15 分
- 累计不及格学分 ≥ 25 → 至少 80 分

**可解释性设计：** 每个因素的 `权重 × 归一化值 × 100` 即其贡献分，六项相加等于风险分。学生看到的"出勤 20.2 分、作业 17.5 分"不是形容词，是可复算的加数。这一设计同时服务于信任与申诉——学生质疑分数时，可以逐项核对。

### 4.3 校规知识库与检索增强

`knowledge/` 目录下收录 6 份文档、24 个条款，覆盖华南理工大学、北京科技大学、上海理工大学、深圳技术大学、上海海事大学及教育部相关政策。

检索采用 **BM25**（中文按字二元切分），返回结果附带学校名与条款标题，直接呈现在回答下方作为引用。

**"一校一规"的可插拔设计：** 更换学校只需新增一个 md 文件。各校规则差异极大——华南理工是 15 学分预警、25 学分降级，北京科技大学是单学期不足 14 学分警示，深圳技术大学是学分不足所选二分之一。通用的"学业预警"产品在这里会直接失效，因为判定标准由每所学校自己定。

### 4.4 文书与数据导出

系统按学生实际数据生成四类文书：学业告知函、家长信、辅导员谈话要点、班级周报。**生成的内容中所有数值来自工具函数，模型只负责措辞。**

文书写成后可一键导出：Word（python-docx 排版，含页眉校名与落款）、PPT 学期报告（python-pptx）、CSV 名单、`.eml` 邮件文件。配置 SMTP 后可直接投递；未配置时产出 `.eml`，本地双击即进邮件客户端——演示环境同样能走完闭环。

## 五、技术路线与系统架构

### 5.1 架构

```
┌──────────── 前端 · Vue 3 + Vite（web/）───────────────────┐
│  /login ┬─ /student   ┬─ /counselor    +  对话面板         │
│         └─ /admin     └─ /parent                          │
└───────────────────────────┬───────────────────────────────┘
                            │ REST JSON ＋ SSE over POST
┌───────────────────────────▼───────────────────────────────┐
│ FastAPI                                                   │
│  ├── 鉴权中间件   PBKDF2 密码 + HMAC token，按角色拦截      │
│  ├── Agent 编排层   意图识别 → 工具调用 → 事实拼装 → 润色   │
│  ├── 风险引擎       加权模型 + 硬规则 + 归因拆解            │
│  ├── RAG            校规知识库（BM25，6 所高校 24 条款）    │
│  ├── 建议层       成因分型 → 引用本人证据 → 策略轮换         │
│  ├── RAG            校规知识库（BM25，6 所高校 24 条款）    │
│  ├── 文书与导出     Word / PPT / CSV / .eml                │
│  └── 数据层         学情模拟数据 + accounts.json + curriculum│
└───────────────────────────────────────────────────────────┘
```

### 5.2 选型理由

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端 | FastAPI + Uvicorn | 与团队 Python 技术背景一致；接口即文档；异步与 SSE 流式支持好 |
| 前端 | Vue 3.5 + TypeScript + Vite 6 | 满足"现代前端框架"要求；组件化让四端共用组件但有独立视图；TypeScript 约束后端载荷 |
| UI 与图表 | Element Plus + ECharts 5 | 表格、抽屉、弹窗开箱即用；ECharts 按需注册 Pie + Bar，不整包引入 |
| 鉴权 | PBKDF2 + HMAC token（自建） | 不引入数据库与第三方身份服务；权限校验放在中间件，前端路由只是第一道 |
| 检索 | BM25（字二元切分） | 语料规模小（24 条款），BM25 精度足够且无需向量库；中文按字切分避免分词器依赖 |
| 导出 | python-docx + python-pptx | 交付物要能打印盖章，纯文本导出不满足场景 |
| 模型 | 任意 OpenAI 兼容接口 | 便于在 DeepSeek / 通义 / Kimi / 本地 vLLM 之间切换，不被单一厂商锁定 |
| 数据 | 确定性模拟数据 | 固定随机种子保证每次启动一致，便于复现与演示 |

**为什么构建产物入库：** `web/site/` 一并提交，评委克隆后无需安装 Node 即可运行，把"能不能跑起来"的风险降到最低；改前端仍走标准 `npm run build`。

## 六、关键技术与创新点

### 创新点一：从"结果性统计"到"过程性预警"，干预窗口前移 8–10 周

不以期末不及格学分为唯一依据，而是把出勤、作业、期中、平台行为等过程性数据纳入评分，在第 8 教学周即可输出风险等级。**这是本项目与现有高校预警系统的根本差异。**

### 创新点二：数值与语言分离的 Agent 架构

Agent 层采用"意图识别 → 工具调用 → 事实拼装 → 语言润色"四段式，**大模型永远拿不到计算权**。

> 成绩与预警是敏感数据，模型编一个分数就是事故。因此所有数字由工具函数计算并返回，模型只负责组织语言。
>
> 未配置 API Key 时，系统用模板拼装同样能完整运行——这不是降级方案，而是把"可信"放在"智能"之前的设计选择。

在普遍"把数据直接丢给大模型"的做法中，这一取舍构成了工程层面的差异化。

### 创新点三：一校一规的可插拔知识库

校规不是背景资料，而是判定依据。系统把每所学校的规则独立成文，检索时按学校定位到具体条款并附引用。新增一所学校 = 新增一个 md 文件，不改代码。

### 创新点四：四端同源、话术降维

同一份数据，对学生讲"你这门课挂科概率 68%"、对辅导员讲"建议本周内约谈，重点问出勤"、对家长讲"孩子最近到课率下降，学校已安排辅导"。**同一引擎、四种表达**，这是把技术能力转化为真实服务价值的关键一环，也是模板化产品做不到的。

## 七、可行性分析

### 7.1 技术可行性

核心组件均为成熟技术：FastAPI 提供接口，BM25 为经典检索算法，加权评分模型无技术风险。**唯一的复杂点是 Agent 编排，而本项目的做法恰恰是限制模型能力范围（只做语言组织），因此风险可控。**

### 7.2 数据可行性

真实学情数据受《个人信息保护法》与校级数据管理规定限制，比赛阶段无法获取，**也不应获取**。项目采用确定性生成的模拟数据（240 名学生、6 个班、6 门课、第 8 教学周，含上学期 GPA 与挂科记录），数据层独立为 `data.py`，接口形态按真实教务系统字段设计，替换为真实数据源时上层逻辑无需改动。

### 7.3 时间可行性

项目周期 4 周（10/21–11/18），功能已按 MVP 锁定范围，**11/05 停止新增功能**，之后全部时间转材料制作与打磨。开发与文档各占约一半时间。

### 7.4 团队可行性

团队成员具备 Python 数据分析与前端开发能力，风险模型的指标设计恰好落在数据科学的专业范围内。分工按交付物划分，每人有明确产出。

## 十、风险分析与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 大模型服务不稳定或额度不足 | 演示中断 | 规则引擎模式兜底，全部核心功能不依赖 Key |
| 校规条款引用过期 | 内容失真被质疑 | 每条标注学校与条款标题，声明"仅用于演示，不作为处分依据" |
| 数据合规争议 | 评审扣分 | 全程使用模拟数据，不接入消费、门禁、社交等非教学数据 |
| 权重设置被质疑主观 | 可信度下降 | 权重集中配置、公开依据来源、支持按校调整 |
| 时间不足 | 作品不完整 | 11/01 锁定范围，停止新增功能，优先保证材料完整 |
| 演示环境故障 | 视频录制失败 | 提前录制备份视频，本地离线包可随时启动 |

## 十一、团队分工

| 角色 | 负责模块 | 具体交付物 |
| --- | --- | --- |
| 成员 A（后端 / 数据） | 风险引擎 + 数据层 | 评分模型、归因拆解、模拟数据生成与校验 |
| 成员 B（前端 / 交互） | 前端 + 交互 | 四端视图、图表、对话面板、响应式适配 |
| 成员 C（Agent / 材料） | Agent + RAG + 材料 | 意图路由、BM25 检索、文书生成、技术文档、演示视频 |

三人共同承担联调、回归测试与文档校核；具体实名信息见大赛报名表与文档封面。

## 十二、伦理与合规声明

本项目在设计与实现中明确以下边界：

1. **系统不作出任何处分决定。** 预警只是提醒，所有升级、降级、退学均需人工核实并遵循学校程序。
2. **不做行为监控的无限扩张。** 仅使用教学相关数据（考勤、作业、成绩、平台学习行为），不引入消费、门禁、社交等数据。
3. **保留申诉入口。** 学生端已实现复核申请，写入跟踪记录并置为"待人工复核"，家长端同时提示可申诉。
4. **数据最小化。** 比赛阶段使用模拟数据，不映射任何真实学生，姓名统一脱敏为编号。
5. **可解释优先。** 所有评分可逐项复算，学生有权知道每个分数的来源。

---

## 十三、结论

学业预警的真正难点不在于"算出风险"，而在于**在还有时间的时候算出风险，并且让拿到结果的人知道该做什么**。

本项目用六维过程性数据把预警时点前移，用可复算的归因拆解把结论讲清楚，用一校一规的知识库让判定站得住，用四端话术降维让同一条信息对不同的人都有用。技术上以"模型不碰数字"为底线，确保系统在敏感数据场景下可信、可审计。

**项目具备清晰的问题定义、可落地的技术路径、可控的范围边界，具备立项条件。**
